# Decisions: archive uploads with server-side extraction

Date: 2026-11-12. For `docs/plans/0010-archive-upload.md`. Builds on the file routes of
`docs/decisions/0001-server-defaults.md` and the charging rules refined through plans 0003–0008.

| Topic | Decision | Why |
|---|---|---|
| Trigger | A `PUT` is extracted when its cleaned path ends (case-insensitive) in `.zip`, `.tar`, `.tar.gz` or `.tgz` **and** the body starts with a recognized archive magic (zip `PK\x03\x04`/`PK\x05\x06`, gzip `\x1f\x8b`, or a tar `ustar` header at byte 257). The archive type is taken from the magic, not the extension: a `.tgz` name holding a zip is unzipped. An archive-looking name whose body matches no magic is `400 not a zip, tar or tar.gz archive`, and an archive body under a non-archive name is stored raw like any other file. | Name-driven means ordinary files are never sniffed and re-extracted behind the uploader's back; magic-driven means lying extensions cannot smuggle a format mismatch. A `400` on a lying name tells the agent the truth instead of storing a broken bundle; someone who genuinely wants a file named `notes.zip` stored raw has the opt-out below. |
| Opt-out | The request header `X-Extract` — present at all, any value including empty — forces the body to be stored and served raw, no inspection. | "Present = keep" is the one rule with no value parsing; a bare `X-Extract` from curl, curl's empty-value syntax `-H "X-Extract;"` and `-H "X-Extract: keep"` all mean the same thing. |
| Destination | Entries land under the **parent directory of the upload name**: `PUT /<hash>/site/bundle.tar.gz` with entries `index.html` and `css/app.css` creates `site/index.html` and `site/css/app.css`; at the bin root the entries land at the root. The archive name itself is not stored, and no directory named after it is created. | Uploading `site.tar.gz` and getting `site/...` is what "upload a folder as an archive" means to a human; keeping the archive's own name too would put a useless 1 MiB blob next to its own contents. Collisions between two archives in the same directory follow normal `PUT` upsert: last write wins per path. |
| Entry validation | The **raw entry name** is judged first, by the existing `cleanPath`: a `.` or `..` segment anywhere, an absolute name, a control character, a backslash (tar keeps them), an over-256-byte or over-16-segment name is refused. The format's conventions come before that check — zip backslashes become `/`, one trailing `/` is the directory marker, and one leading `./` is the `tar czf - .` idiom, while a repeated `././x` is refused by the same rule as any other `.` segment. What is left empty is the archive's own folder: checked and skipped for a directory, `400 archive contains an unnamed entry <name>` for a regular file. The combined path (`dir + "/" + validated entry`) then runs through `cleanPath` a second time as the belt-and-braces check, which is where an entry that fits on its own but not under a deep folder is refused for length or segment count. A tar header whose name field carries bytes past its NUL terminator is `400 archive contains an entry name with a NUL byte <name>`, checked by walking the tar block layout over a bounded streaming read: `archive/tar` stops reading a name at the first NUL. Whole-archive refusal is unchanged. | Tightened at review because judging `path.Join(dir, entry)` after `Join` had already cleaned it let `sub/../up.txt` move up to `site/up.txt`, `deep/../../evil.txt` land as `evil.txt` at the bin root, and `/etc/passwd` relativize to `site/etc/passwd`, while the very same entry in a root-level archive was refused. Judging the name the archive actually wrote is what this document promised, and `cleanPath` is still the guard doing the refusing. The NUL rule closes the sibling quirk the review found the same way: a crafted tar stored its entry under the truncated name. |
| Non-regular entries | Any archive entry that is not a regular file — symlink, hardlink, device, fifo — fails the **whole** archive with `400` naming the entry. Tar global/pax header records and directory entries are not files: directories are validated but not stored (sandbin directories exist only as path prefixes), global headers are skipped. | A symlink in a bin has no meaning — sandbin serves blobs, not a filesystem. Silently skipping a symlink drops data the uploader thought they sent; silently replacing it with a blob whose content is the link target invents a file. A loud 400 makes the archive match what the bin can hold. |
| Size and count caps | The 1 MiB request body cap is unchanged (the archive file itself). Inside it: each entry ≤ 1 MiB uncompressed, at most 1000 entries, and at most 32 MiB unpacked in total per archive. Cap breaches answer `413` (`extracted file over 1 MiB`, `archive unpacks over 32 MiB`, `archive has over 1000 files`); format and safety refusals answer `400`. | 1 MiB per entry is the cap every bin file already has, so extraction cannot be a way to smuggle a bigger file in. The total cap and entry count bound a decompression bomb: reading each entry through a limit reader means a 1 MiB zip claiming 4 GiB stops at 32 MiB of server memory, not 4 GiB. 413 vs 400 follows the repo's existing precedent of size limits being 413. |
| Duplicate entries | Two entries with the same cleaned path fail the whole archive with `400 archive contains duplicate path <path>`. | Tar cannot hold duplicates, so one is a broken archive; zip can, and which one "wins" is archive-tool folklore — a refusal beats picking a winner from a malformed input. |
| Empty archive | An archive whose entries are all directories (no regular file at all) is `400 archive contains no files`; nothing is stored. | A successful-looking upload that stored nothing is the one outcome an agent cannot notice from the response; refusing names the surprise instead. |
| Atomicity | Extraction stores all entries or none: a new `Store.PutFiles(binHash, []FilePut) (created, replaced int, err error)` runs one transaction containing the same upsert `PUT` performs per path. A parse, validation or store failure mid-archive leaves every existing file untouched. | A half-extracted bundle is the worst state for the preview use case: it looks like the upload worked. One transaction is also exactly how `PutFile`'s mirror semantics work for a single file, just batched. |
| Upsert, not sync | Extraction replaces paths it names and leaves every other file in the bin alone; it never deletes files that the archive does not mention. Status is `201` when at least one path was newly created, `200` when every path was a replacement. | Bin semantics today are per-path upsert (plans 0001 onward); a sync-or-delete mode is a different product decision about bin lifecycle that nobody has asked for. |
| Response | `201`/`200` as above, `Content-Type: text/plain`, a `X-Extracted-Count: <n>` response header, and a body listing every extracted file as one `/<hash>/<path>` per line — the same line a plain `PUT` answers, pluralized. | The body is the human-readable half and matches what a normal PUT already says; the header is the machine-readable half, so a script never has to parse the body to learn the count. |
| Charging | Nothing about charging changes: only API-key failures and blocked attempts charge (plans 0003+). A bad archive — 400 or 413 — happens after the key check and charges nothing, exactly like a bad upload path today. | Extraction is a kind of `PUT`, and the repo's charging rules are about authentication attempts, not request validity. |
| Formats | Only zip (via `archive/zip`), raw tar and gzipped tar (via `archive/tar` + `compress/gzip`), all stdlib. `.tar.bz2`, `.7z`, `.rar`, bare `.gz` of a non-tar are stored raw like any other file; no extraction tooling, no subprocesses. | The client agent ecosystem produces exactly these two formats with `zip` and `tar czf`. Stdlib-only is a property of this codebase (no new dependency, same container), and any exotic format would need a third-party library for a guess nobody asked for. |
| No recursion | An extracted entry named `inner.tar.gz` is stored as a blob; extraction runs once per request, never on entry content. | Recursive unpacking multiplies every size cap by depth and turns one 1 MiB request into unbounded work. An uploader who wants the inner archive extracted PUTs it again. |
| After extraction | Extracted files are ordinary bin files: served raw, ANSI-rendered, listed, and an `index.html` at the bin root becomes the bin's cover page. Nothing records or reveals that a file came from an archive. | The feature's whole point is that an archive upload is indistinguishable from uploading the same files one by one. A "this came from a zip" marker would be trivia after the fact. |
| Client shape | The client gains `--no-extract`, which sends `X-Extract` on the uploads of that run. When a `PUT` answer carries `X-Extracted-Count`, the client's result line becomes `extracted <n> files into <url>` instead of the created/updated line. `--archive <folder>` builds the archive client-side (next row); the README still shows `tar czf - dir | sandbin-client --name site/bundle.tar.gz` for people who want to make the archive themselves. | The result line is shaped so an agent reading stdout sees the count without parsing. A hand-built archive stays a first-class recipe because zip is not something the client builds, and raw upload of an existing archive file needs no new machinery. |
| Client archive mode | `--archive <folder>` builds a `.tar.gz` client-side and uploads it. Tar entries carry the **folder's cleaned path relative to the current directory verbatim** — `--archive hello` yields entries `hello/world.html` — and the archive is uploaded **at the bin root** named `<basename>.tar.gz` (`hello.tar.gz`, and for `--archive projects/app` also `app.tar.gz` while entries still read `projects/app/...`). With the server's parent-directory placement, bin paths then come out exactly folder-relative: `./hello/world.html` becomes `/<hash>/hello/world.html`. The tar is written to an `os.CreateTemp` temp file, uploaded, and removed on every exit path including failures. Non-regular entries in the folder (symlinks, devices, fifos) are refused client-side with the same honesty the server applies to archives; directory walking uses `filepath.WalkDir`, which is lexicographic, so runs are deterministic. `.`/`./` and absolute folder arguments are refused: the base path of a bin must name a folder. | Entries must carry the base path or the folder's name is lost, and the archive must sit at the root or the server's placement rule would double a nested folder's parent (`projects/app.tar.gz` placed under `projects/` plus an entry `projects/app/...`). A temp file (not a pipe) lets the client measure the compressed size before spending an upload, and it is the literal thing being uploaded. Refusing symlinks locally beats shipping an archive the server is certain to reject. |
| Client-side cap mirroring | Before building: refuse a folder with a regular file over 1 MiB, over 1000 regular files, or over 32 MiB in total; after building: refuse an archive file over 1 MiB. All refusals happen with zero requests, like `cleanMetadata` does for metadata. | The server will refuse all four anyway; discovering them after a wasted upload is the difference between an agent getting a usable message and getting a transport error. The compressed-size check is only possible once the temp file exists, so it is the one post-build check. |
| Archive composition | `--archive` combines with file arguments, stdin and `--name` in one run; the archive upload happens after them. Piped stdin with no `--name` is refused in an `--archive` run with the same words every other run uses — `--archive` does not make what was piped in meaningless — which is what review tightened, because an `--archive` run used to drop it silently. `--archive` with `--no-extract` uploads the built tar.gz raw — the bin then holds the single archive file. Metadata flags, bin resolution and the state file are untouched. One `--archive` per run. | The flat client already interleaves args and stdin; appending one more upload is the same shape. Raw mode is the obvious "send the folder as one file" companion. One folder per run keeps the single derived upload name unambiguous. |
