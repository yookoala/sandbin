# Decisions: deleting files and folders, and the 404.html fallback

Two bin-semantics features asked for at once; they touch different code paths and are planned
as five atomic commits in `docs/plans/0013-delete-and-spa.md`.

| Point | Decision |
|---|---|
| SPA fallback shape | GitHub Pages shape, per explicit user choice: when a `GET` under a bin matches no file and the bin holds **`404.html` at its root**, serve that file's bytes with `Content-Type: text/html` and keep **status 404**. The SPA router in the served page takes the route from the URL. No `X-` marker header, no status rewrite to 200, no separate fallback config — the file's presence is the whole setting. Netlify/Vercel-style 200 fallback was considered and rejected as needlessly complex. |
| Fallback reach | Unmatched, cleaned, non-empty subpaths only. The bin base keeps its existing answer (index.html or the directory listing). A match always wins: a real file named like the route is served normally. `404.html` itself, requested exactly, is a normal file (`200`). Only the root `404.html` counts — `hello/404.html` is just a file. The name is matched exactly and case-sensitively, mirroring the `index.html` root check. `GET` only: PUT/DELETE/PATCH never fall back. A protected bin answers `401` before any lookup, as every GET does. With no root `404.html`, the plain `404 unknown path` stands unchanged. |
| DELETE surface | `DELETE /{hash}/{path}` deletes exactly that file. `DELETE /{hash}/{folder}/` — the trailing slash is the folder marker — deletes every file under `folder/` (a path counts when it starts with `folder/`; `helloworld/x` is never caught by `DELETE hello/`). An empty folder match and a missing file are both `404 unknown path`. The bin itself is never deleted: `DELETE /{hash}/` answers `405` like every other method on the base; `DELETE /` at the root, and DELETE on `/healthz`, `/verify-key`, `/skills/...`, keep their existing refusals. An emptied bin survives, base listing and all. |
| Trailing-slash rule | The "no trailing slash" rule lives in `cleanPath`, called per handler — not a global guard. The DELETE handler trims one trailing slash from `sub`, runs `cleanPath` on the remainder, and treats a `sub` that was slash-terminated as the folder form. Every other method's path rules are untouched, including their 400s for trailing slashes. |
| DELETE authority | DELETE joins the key-checked family: blocked address answers `429` with `Retry-After` and counts as another failure; a wrong or missing key is `403` and charges the lockout exactly like `POST /`, `PUT` and `POST /verify-key`; a right key then reaches `404 unknown bin`/`unknown path` with no further charge. A password-protected bin requires Basic Auth (user name = bin hash), as every GET and PUT below it does; a wrong bin password is `401` and charges nothing. Guard order mirrors `putFile` block-for-block. |
| DELETE answer | `200` with a JSON body `{"deleted":["<path>", …]}` — paths are bin-relative; a single file lists its one path, a folder lists every path it removed, sorted. The client renders one `deleted <url>` line per path from it. |
| Folder delete implementation | `ListFiles` for the bin, keep paths where `strings.HasPrefix(path, folder+"/")`, delete them all inside one store transaction, answer that list. Chosen over SQL `LIKE`/range tricks because bin folder names can legitimately hold `%` and `_` and the escaping footgun is not worth a query; bins are preview-sized and already listable. All-or-nothing like archive extraction. |
| Client delete flags | `--delete PATH` and `--delete-folder NAME`, both repeatable (a `flag.Var` collecting values, so order as given is kept). `--delete` takes a file path and refuses one ending in `/` with a pointer to `--delete-folder`; `--delete-folder` validates the name with the existing local name rules and sends `NAME + "/"`. A delete run uploads nothing: file arguments, piped stdin with `--name`, `--archive` and `--new` are each a loud refusal, the way `--describe` is its own run; `--describe` with a delete is refused too. Bin metadata flags combine: they apply first, then the deletes. The bin comes from `.sandbin.yaml` / `--bin` as always; `SANDBIN_BIN_PASSWORD` goes as Basic Auth. Output is one `deleted <url>` line per path; a `404` surfaces as an error naming the path. Exactly one request per delete, no retries, same lockout warning as uploads. |
| Docs ripple | README: DELETE + fallback paragraphs in the API section, DELETE added to the key-checked verb list in the lockout section, a delete subsection in the client section. Front page: one clause in the bin paragraph naming both behaviors; `TestFrontPageAtRoot` marker updated. SKILL.md: a short "Deleting files and folders" section and a fallback sentence in the intro. |

## Added after shipping: the missing slash on a bin base

| Point | Decision |
|---|---|
| `GET /{hash}` without its slash | GitHub-style 301 to `/{hash}/`, the query string carried into the `Location`. Only for GET and only when the hash is an existing bin; unknown hashes and every other method (PUT/PATCH/DELETE/HEAD/OPTIONS) keep the old `404 unknown bin` — redirecting a write would silently change what it meant, and answering 301 for unknown hashes too would turn every mistyped URL into a cheaper existence oracle. A protected bin redirects too: its existence is already public at `/{hash}/` (401 against 404), so the redirect leaks nothing new. Nothing charges: the whole feature is GETs and 404s. Lives in `ServeHTTP`'s no-bin-segment branch beside a `singleSegment` helper; static routes and the `.`/`..` refusals keep answering first. |

## Skipped on purpose

Deleting the bin itself (any form), recursive delete without the slash marker, fallback for
non-GET methods, a 200-status fallback variant, per-path permissions, delete history/undo, bulk
or batch APIs beyond the folder prefix, and serving `404.ansi` or nested `404.html` as a shell.
