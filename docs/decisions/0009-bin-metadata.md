# Decisions: bin title and description

Date: 2026-11-12. For `docs/plans/0009-bin-metadata.md`. Adds metadata to the bin rows from
`docs/decisions/0001-server-defaults.md`; everything settled there (hashes, passwords, 1 MiB body
cap) stays.

| Topic | Decision | Why |
|---|---|---|
| Carrier | `X-Bin-Title` and `X-Bin-Description` headers on `POST /` (creation) and `PATCH /<hash>/` (update); the same two headers answer a bin-base `GET` | The repo already carries authority in headers (`X-API-Key`, `X-Bin-Password`), so a second carrier mechanism (a json body API) would double the surface. HTTP headers are single-line, which settles metadata as single-line text — good enough for "communicate or record about the data" and keeps every piece of it greppable in one response. |
| Update method | `PATCH /<hash>/`, the bin base only; a present header replaces its field, an absent header leaves it, an empty value clears it. A header value over the limit is `400 title over 200 bytes` / `400 description over 2000 bytes`. | `PUT /<hash>/` is already refused as "empty path" and `POST /<hash>/`/`DELETE` are 405 today, so `PATCH` at the base adds no collision. Field-merge semantics (COALESCE in one UPDATE) make a partial update atomic without a read-merge-write race. |
| Limits | Title ≤ 200 bytes, description ≤ 2000 bytes, counted as UTF-8 bytes; control characters (< 0x20 or 0x7f) refused. Measured client-side with mirrored wording so a bad flag fails before a request, like upload names do. | Bytes is how the repo already measures (`maxPathLen`, the 72-byte bcrypt cap, 1 MiB), and argv can carry newlines, so the client must not trust the transport. 200/2000 is a name and a paragraph. |
| Auth and charging | A wrong API key on `PATCH` charges the address exactly like `POST`/`PUT` (blocked attempts charged); a wrong bin password on `PATCH` is a 401 and charges nothing, exactly like `PUT`. `--describe`/`GET` needs no key for an open bin and charges nothing. | Metadata is a bin write, so it takes the bin-write rules; reading metadata is reading the bin, which is already gated by `binAuthorized` for protected bins. |
| Visibility | A bin-base `GET` (listing or raw index.html) carries the two response headers when the values are non-empty, and the generated listing shows title in `<title>`/`<h1>` and description in a `<p>` — escaped. A stored index.html is still served raw with nothing injected (its author owns that page); its bin's metadata is in the headers. A listing with no metadata renders byte-identical to today. | The metadata's purpose is agents reading it, so headers (machine route) and the listing page (human route) both carry it. Injecting text into an author's own index.html would break the raw-serving shortcut the code already documents. |
| No json API | No `GET /<hash>/?json` or dedicated metadata route. Machine-readable read is the two response headers plus `sandbin-client --describe`, which prints `title:`/`description:` lines. | One json shape for the bin would have to grow a file list to be useful, which is a bigger API decision than this feature; the headers plus two client lines answer "what is this bin" today. |
| Storage and migration | `bins` gains `title TEXT NOT NULL DEFAULT ''` and `description TEXT NOT NULL DEFAULT ''`. `openStore` runs the schema, checks `pragma table_info(bins)` and `ALTER TABLE bins ADD COLUMN` for whichever is missing. Old bins read as empty metadata. | `CREATE TABLE IF NOT EXISTS` alone never adds columns to an existing db, and live dbs exist (the container volume). An old binary seeing a new db is fine: its inserts name columns and the defaults fill in. |
| Client shape | The flat single-FlagSet client stays. `--title` / `--description` set metadata: on a created bin they ride the creation `POST` (no extra request), on an existing bin they are one `PATCH` right after the bin is resolved, before uploads. A metadata-only run is allowed when at least one of them is given. `--describe` is read-only: one `GET`, no API key required for an open bin, refused together with uploads or `--new`. | The client's existing shape is agent muscle memory; verbs would break every shipped invocation. `--describe` without a key mirrors the server's own read rules. PATCH before uploads means a later upload failure still leaves the description that documents what was meant. |
| State file | `.sandbin.json` gains nothing. The server is the source of truth for metadata; `--describe` reads it from there. | Storing a copy in the state file creates a second truth that a `PATCH` from elsewhere would silently invalidate. |
