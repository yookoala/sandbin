# Decisions: the init re-initialization guard, and the installer running init

Two linked client behaviors: re-running `init` in an already-initialized project must be an
explicit act, and the installer one-liner should also initialize the current directory, asking
only for the API key. Plan in `docs/plans/0014-reinit-guard-and-installer-init.md`.

| Point | Decision |
|---|---|
| "Already initialized" | `.sandbin.yaml` exists and parses with **both** `sandbin_url` and `api_key` non-empty. A partial file (one field empty) is not initialized — `init` proceeds exactly as before. The file, not the environment, is the marker: `SANDBIN_URL`+`SANDBIN_API_KEY` alone never trigger the guard. |
| Guard mechanics | At a terminal: a warning naming the url, then a `re-initialize? [y/N]: ` question before the normal wizard; `y`/`yes` (case-insensitive) continues the wizard, everything else — including bare Enter and EOF — cancels with `left the existing initialization for <url> untouched` and exit 0. Nothing is read or written beyond that question. Non-terminal: no question is asked (nobody is there to answer it) and the run refuses with `sandbin-client: .sandbin.yaml is already initialized for <url>: pass --reinit to overwrite it, or delete the file to start over`, exit 1. |
| `--reinit` | The explicit consent for scripts: `init --reinit` skips the question entirely and re-initializes, keeping today's semantics (re-verify the key, rewrite, and keep the file's `bin`/`protected` when the url is unchanged). On a directory that is not initialized `--reinit` is a harmless no-op. Passing `--url`/`--api-key` is NOT consent — supplying new values is exactly the overwrite the guard exists to confirm; only `--reinit` or a `y` answer is. Flag-only design was offered and a question-only design considered; the user chose keeping both so agent/CI flows get a one-line self-documenting path. |
| Guard order and charging | The guard runs after flag parsing and `readConfig` and before the value ladder, any prompt, `POST /verify-key` and any write. A refused re-init therefore sends no request: even `init --api-key <wrong>` over an initialized project charges nothing (proven live against the block table). The guard never echoes the stored key; the url is public-ish and already printed by every successful init. |
| Wizard unchanged otherwise | The url/key prompts keep their terminal-only reading and flag > env > file ladder. A confirmed re-init at a terminal usually prompts for neither url (file default shown) nor key (the file's key feeds the ladder); changing the key interactively means `init --api-key new` and answering `y`. |
| Installer init step | After a successful client install, when the client binary exists the installer runs `"$CLIENT" init --url "$BASE" </dev/tty`. Redirecting from `/dev/tty` is mandatory: the script itself arrives through stdin (`curl | bash`), so an init reading stdin would eat the rest of the script. The step is gated on stdout being a terminal (`[ -t 1 ]`) and `/dev/tty` actually opening; otherwise the installer prints the exact command to run instead and still exits 0. At a terminal in a fresh directory this asks exactly one question — the api_key — because the url arrives via `--url`. In an already-initialized directory the guard question itself arrives through `/dev/tty`: answering `n` leaves the project alone (init exit 0) and the install stands; `--reinit` is not passed by the installer — the question is the human path. |
| Installer failure discipline | A failed init (wrong key, refusal, cancelled wizard) prints a `sandbin-installer:` warning naming the exact command (mentioning `--reinit`) and the installer still exits 0: the skill files are installed regardless. No go / failed `go install` means no client binary, so the init step is skipped entirely — the skill's build-on-first-use flow remains the only flow. `set -euo pipefail` stays; the init call is guarded with `||`. |
| Non-terminal installer behavior | Agents and CI runs get the hint line `sandbin-installer: run "<path> init --url <base> --api-key YOUR_KEY" to finish setup` on stderr, exit 0. SKILL.md already teaches agents to run init themselves with `--api-key`; the guard wording there tells them about `--reinit` and the delete-the-file path. |
| Docs ripple | README install section: the installer now initializes the current directory with a single key question, and the non-terminal hint wording. README init section: the guard paragraph with verbatim refusals and `--reinit`. Front page: one clause under the skill install paragraph naming the key-question behavior; `TestFrontPageAtRoot` marker extended. SKILL.md: guard sentence in the init section (`--reinit`, delete-to-start-over). install.sh header comment updated. |

## Skipped on purpose

Piped `y` answers to the guard question (the user chose the flag instead), remembering consent
per project, any `--force`-style alias, a server-side notion of initialization, guarding partial
configs, prompting when only url or only key is set, and letting the installer force
`--reinit` or pass an `--api-key` through.
